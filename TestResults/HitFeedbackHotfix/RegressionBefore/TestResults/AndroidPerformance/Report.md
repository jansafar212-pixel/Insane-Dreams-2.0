## Diagnosis and baseline

Before production edits, captured the real Warehouse_Demo in advancing Play Mode:
15 authored actors, seeded RNG, protected player, alternating retreat/aim and fire
inputs, 120 warm-up frames, then 600 measured frames. Unity CPU Profiler enabled,
Deep Profiling disabled. Inclusive CPU markers sampled over the final 60 frames.
Separate warmed 200-call probes isolate unchanged UI and pose work.

Three largest relevant measured CPU categories were:

1. Character/presentation LateBehaviourUpdate: 1.051 ms/frame. Repeated sprite
   changes nested in this work cost 0.473 ms/frame. CharacterVisualDriver assigned
   a skin fallback and then the equipped override every frame, repeatedly dirtying
   sprite geometry even though the final image did not change. Full player pose
   probe cost 220.87 microseconds/call in the initial capture.
2. RenderPlayModeViewCameras: 0.948 ms/frame (includes URP rendering, not GPU time).
   Sprite invalidation contributes extra renderer work. No evidence warrants
   lowering resolution, changing art, disabling lights/effects or building atlases
   without a device GPU/Frame Debugger capture.
3. BehaviourUpdate: 0.331 ms/frame. A localized avoidable component is HUD readout
   formatting: unchanged HUD refresh 15.41 microseconds/call; mission clock/readout
   2.47 microseconds/call. Repeated formatting occurs on existing 0.2/0.15-second
   schedules, not every rendered frame; revive-offer text was formatted each frame.

These categories overlap (inclusive markers); do not add them together. They are
the Editor workload's ranked categories, not a claim about the device's top three
bottlenecks. Physics2D.Simulate averaged 0.059 ms in this sample, so global physics
timing/joints/collision behavior were preserved rather than weakened speculatively.

## Implementation

- `Assets/Scripts/Visuals/CharacterVisualDriver.cs`: resolve final equipped weapon
  sprite once, set only when changed. No transient skin-to-equipment swap each pose.
- `Assets/Scripts/Visuals/CutoutRig.cs`: skip identical face/magazine sprite setters.
  Existing pose calculations, reload resets, limbs, pivots and animation times stay.
- `Assets/Scripts/Input/WarehouseTouchControls.cs`: value snapshot before readout
  formatting. Invalidate on bind/enable; include ammo/capacity/reserve, selection,
  grenade stocks, reload, health, armor, healing, protection and supply state.
  Preserve existing readout cadence; inputs and contextual buttons still update
  every frame. Cache unchanged revive-offer caption. No UXML/USS/layout changes.
- `Assets/Scripts/Missions/MissionHud.cs`: format mission clock when the displayed
  whole second changes, retaining the current interaction/readout schedule.
- `Assets/Scripts/Camera/AndroidFramePacing.cs`: Android-only BeforeSceneLoad
  initializer requests 60 FPS instead of platform-default `-1`; desktop and physics
  timing unchanged. No camera-controller edits.
- Editor-only tests: AndroidPerformanceCaptureTests and
  AndroidPerformanceRegressionTests; no profiling fixture code ships in the APK.
- Development log/checkpoint and evidence in this folder. New script `.meta` files
  are generated by Unity; no scenes, prefabs or native serialized assets edited.

No new manager, pooling framework or dependency. Normal tracers, flashes/impact
sprites, fireworks and thrown grenades already have bounded reusable pools.
Enemy spawning prewarms authored actors. Ragdolls already sleep, wake on impacts,
cap velocity and retire by lifetime/registry limits. AI already samples LOS and
position/cover decisions with bounded buffers. These systems remain intact;
no offscreen AI suppression, new decision delay or reduced visual intensity.

Editor runs are noisy, frame-based input patterns run for different wall durations,

ordinary advancing-animation frame cost. No sustained frame-pacing claim is made.

before / 3.45 GB final. The session includes retained profiler/test/import state;
this is not comparable Player memory or proof of a gameplay leak/improvement.
Draw-call/batch, GPU, thermal, touch latency and device memory require Player captures.

Allocation correction: GC.GetAllocatedBytesForCurrentThread returns zero even for
a known 8 KiB allocation here (AllocationCounterCheck.json). Baseline probe byte
zeros and the earlier camera zero-byte figure are unsupported. Later probes use

## Exact Galaxy A56 profiling procedure

1. In Unity Build Profiles choose Android, current enabled scenes beginning with
   MainMenu. Retain IL2CPP, ARM64, minimum API26, current LandscapeLeft orientation,
   URP render scale1 and existing point-filtered textures. Optimized Frame Pacing
   is already enabled; do not alter physics fixed timestep (0.02 seconds).
2. Create a **Development Build**, **Autoconnect Profiler** on, **Deep Profiling**
   off, Script Debugging off. Export APK. A native CLI dry-run/build uses:
   `unity command build --target Android --outputPath build/AndroidPerformance/AKUMU2-profile.apk --options '["Development","ConnectWithProfiler"]' --dry_run true --caller plugin --skill unity-cli --format json`
   Then repeat with `--confirm true` instead of `--dry_run true`. Use the installed
   Unity CLI path if `unity` is not on PATH. Check build_status to completion.
3. Enable USB debugging, connect/unlock the A56, authorize this PC. Check
   `adb devices -l`, install with `adb install -r build/AndroidPerformance/AKUMU2-profile.apk`.
   Select AndroidPlayer in Window > Analysis > Profiler. Use a fixed phone refresh
   setting, brightness, graphics, resolution and thermal/battery conditions.
4. Record CPU Timeline/Hierarchy, Rendering, Memory, Physics2D and GPU where
   supported. Use brief separate allocation-callstack captures; avoid Deep Profile
   overhead during timing. Inspect actual draw calls/batches, sprite overdraw,
   materials and passes using the supported Frame Debugger connection. Do not
   infer GPU time from CPU render markers or treat unsupported zero GPU time as data.
5. Warm up the same route. Capture comparable normal movement, retreating while
   shooting, multiple Larpers firing/reloading, Samurai pursuit, Officer laser/shot,
   fireworks, smoke/frag/flash, several live ragdolls, rapid weapon switches, ladder
   and parachute. Preserve enemy count/behavior. Repeat three times per build.
6. Run for at least 15 minutes; capture representative intervals near start,
   middle and end. Record heat/thermal throttling, Player used/reserved memory,
   GC.Alloc, active-body/physics time and any exceptions. Save raw Profiler captures.
   Short USB profiling captures and a second non-Development release run are both
   needed because profiling overhead changes timing/thermal behavior.
7. Export frame durations from recorded captures. Compute mean FPS as 1000/mean(ms),
   median, p95/p99, and 1% low as 1000/mean(slowest 1%). Separate active CPU work,
   Render Thread/GPU and WaitForTargetFPS; do not call intentional 60 FPS waits a
   bottleneck. Target approximately16.67ms, preferably13-14ms useful-work headroom.
8. Compare a retained, known identical pre-optimization build with this revision;
   old0033 APK predates the camera and is not an equivalent performance baseline.
   Record camera/joystick feel and visual parity separately from FPS. Confirm no
   stale HUD values, reload/grenade bugs, pose changes or lost offscreen awareness.
